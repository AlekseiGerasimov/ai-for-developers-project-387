Приложение перенесено из проекта 386. [Исходная спецификация и решения](docs/agents/project-origin.md).
Текущий трекер: https://github.com/AlekseiGerasimov/ai-for-developers-project-387/issues.

## Агент в GitHub

### PR, независимое ревью и бюджет

[pr-review.yml](.github/workflows/pr-review.yml) отдельно запускает обычный
OpenCode CLI на `pull_request`: opened, synchronize, reopened, ready_for_review.
Критерии из [REVIEW.md](REVIEW.md), diff, описание и обсуждение PR, публичные
issue по ссылкам в описании и результаты CI передаются модели как вложения.
Размещайте ссылки на исходное обращение, спецификацию, каждый тикет и комментарий
согласования в описании PR. Недоступный контекст ревьюер отмечает как пробел.
CLI работает в отдельном временном каталоге, все инструменты запрещены настройкой
permissions; код PR не исполняется. Комментарий публикует отдельный шаг через
`gh pr comment`. OIDC здесь не используется. Параметры CLI:
[официальная документация](https://opencode.ai/docs/cli/commands/).

Ревью получает contents/issues/actions/checks/statuses: read и pull-requests: write.
Допускаются только публичный репозиторий, его собственные ветки и доверенные
авторы OWNER/MEMBER/COLLABORATOR либо явно разрешённые `opencode[bot]`,
`opencode-agent[bot]` (REST login автора ответа установленного приложения в issue #3) и
`github-actions[bot]`. Если установленное приложение имеет другой login, владелец
должен проверить его и обновить allowlist. Fork не получает секрет модели.
Тайм-аут задания 15 минут, модели 10 минут; concurrency отменяет устаревшее ревью.
Публикация проверяет актуальность SHA. Ревью не вызывает исправление: человек
передаёт замечание командой `/oc` в обсуждении или на строке diff.

В `opencode.yml` перед установкой инструментов и моделью проверяется бюджет:
три попытки на PR суммарно для обоих каналов комментариев, включая run_attempt
при Re-run, отмены и тайм-ауты. Источник — история Actions с actions: read,
не редактируемый агентом комментарий. Считаются только запуски с успешным
authorize; отклонённые комментарии не расходуют бюджет. Re-run старого запуска
учитывает и более новые допущенные команды, чтобы нельзя было обойти лимит.
При недоступности истории модель не вызывается, отдельное задание сообщает infra.
Автоматическое ревью учитывается отдельно и не расходует эти три попытки.
Лимит действует при сохранённой истории и конфигурации workflow; администратор
может изменить условия, новый PR получает новый бюджет. После исчерпания модель
не вызывается, публикуются `limit_exhausted`, SHA и ссылка на логи. Отдельное
задание сообщает infra/timeout/agent_failed; неоднозначную причину сверяют по логам.
Модель имеет тайм-аут 15 минут при 20 минутах задания реализации.
Причину отказа и SHA публикует отдельное задание `report` без модели, checkout
и OPENAI_API_KEY. Только у него есть pull-requests: write для комментариев PR;
у задания модели остаётся pull-requests: read. Бюджетный шаг передаёт reason/SHA
через outputs и не пытается публиковать с токеном чтения PR.
У GitHub App реализации также должно быть только Actions: read: права GITHUB_TOKEN
не ограничивают отдельный токен приложения. Проверить это в настройках установленного
App перед демонстрацией; токен с Actions: write может удалять историю и нарушить лимит.

CI проверяет точный head SHA PR, сохраняет `tested-sha.txt` и Playwright trace
даже после успеха в артефакте `browser-<SHA>`. Перед мержем человек открывает
артефакт, сверяет SHA с текущим head и сценарии со спецификацией. После push
проверка повторяется. Шаблон PR содержит проверки, риск и откат.

Настройки владельца и демонстрация (локальные изменения их не выполняют):

1. Добавить OPENAI_API_KEY и проверить allowlist приложения; сначала включить
   workflow и REVIEW.md в основной ветке, затем открывать PR реализации.
2. В исходном issue вызвать implement-spec со ссылками на согласованную
   спецификацию и тикеты. Проверить ссылки, Closes, риск и доказательство
   отказа теста на базовой версии и успеха после исправления.
3. Оставить общий и построчный `/oc`, разобрать замечания, проверить правки
   в той же ветке и превратить один дефект в регрессионную проверку.
4. На учебном PR после трёх попыток вызвать `/oc` ещё раз: сохранить ссылку
   на отказ без Run agent. Проверить также Re-run и оба канала комментариев.
5. В Settings → Rules → Rulesets включить обязательный успешный `check` для
   main. Если тариф не позволяет, зафиксировать ограничение и вручную сверить
   статусы текущего SHA. Решение о мерже оставить комментарием человека.
6. Проверить Conventional Commits новых коммитов и итогового squash-заголовка.
   В Settings → Actions → General → Workflow permissions разрешить Actions
   создавать PR. После мержа существующий release-please создаёт release-PR;
   при прежнем запрете повторить неуспешный запуск. Для PR от GITHUB_TOKEN
   проверить ожидающее ручное подтверждение CI. Опубликованную историю не менять.

Workflow [opencode.yml](.github/workflows/opencode.yml) вызывает OpenCode для разбора
issue, подготовки спецификаций и тикетов, реализации и правок PR. OpenCode выбран
как готовая интеграция с GitHub; модель задаётся отдельно: `openai/gpt-6.1-sol`.
Команды `mentions: /opencode,/oc` указаны явно. `share: false` отключает публикацию
сессий; ответы в публичных issue и логи Actions остаются видимыми.

Ручные события: `issue_comment` (issue и обсуждения PR) и `pull_request_review_comment`
(строки diff), только `types: [created]`. Команды принимаются отдельным словом,
без учёта регистра, от `OWNER`, `MEMBER`, `COLLABORATOR` с типом аккаунта `User`.
Комментарии ботов, отредактированные комментарии и PR из fork не вызывают модель.
Источник PR проверяется через API даже для комментариев доверенного автора.

Предварительное задание `authorize` имеет только чтение contents, issues и PR,
тайм-аут 2 минуты; оно проверяет также доступ к текущему issue. Задание агента
имеет `contents: read`, `issues: write`, `id-token: write`, checkout с `persist-credentials: false`.
Ответы, ветки и PR агент публикует с правами GitHub App через OIDC.
Для команд `gh` передан `GH_TOKEN` с правами чтения репозитория и записи в Issues;
работа с ветками и PR использует отдельную авторизацию GitHub App.
Тайм-аут агента — 20 минут; `concurrency` допускает один активный запуск на номер
issue/PR (`cancel-in-progress: false`). Новый запуск не прерывает текущий;
GitHub может заменить ожидающий запуск при нескольких новых командах.

Чистый раннер получает проектные скиллы из `.agents/skills/`: OpenCode обнаруживает
этот каталог автоматически. Перед запуском проверяются `triage`, `to-spec`, `to-tickets`,
`implement-spec`, `AGENTS.md` и настройки в `docs/agents/`. Через mise устанавливаются
версии инструментов проекта, npm-зависимости и Chromium для браузерных тестов.
Основная проверка: `mise run check`; отдельно тесты — `mise run test`, линтеры —
`mise run lint`. Трекер — [Issues проекта 387](https://github.com/AlekseiGerasimov/ai-for-developers-project-387/issues).

### Подключение и проверка

1. Установите [GitHub App opencode-agent](https://github.com/apps/opencode-agent)
   только на репозиторий `AlekseiGerasimov/ai-for-developers-project-387`.
2. В [Settings → Secrets and variables → Actions](https://github.com/AlekseiGerasimov/ai-for-developers-project-387/settings/secrets/actions)
   добавьте `OPENAI_API_KEY` с доступом к выбранной модели. Ключ хранится только в
   Secrets; в issue, файлы или чат его не вставляйте. Доступность модели зависит
   от проекта OpenAI. При желании настройте бюджет у провайдера.
3. Проверьте события, права, модель, `mentions` и `share` в workflow перед первым вызовом.
4. Создайте проверочное issue с просьбой прочитать `AGENTS.md` и `docs/agents/`,
   назвать трекер, скиллы и команду проверок. Оставьте комментарий `/oc explain this issue`.
   Для спецификации пример команды: `/oc запусти скилл to-spec по обсуждению этого issue`.
5. Результат — комментарий приложения в том же issue/PR; выполнение и ошибки —
   в [Actions → OpenCode](https://github.com/AlekseiGerasimov/ai-for-developers-project-387/actions/workflows/opencode.yml).
   Сводка запуска содержит трекер, основные скиллы и команды проверок.

Остановить текущую работу: Actions → OpenCode → запуск → Cancel workflow.
Отключить новые запуски: меню workflow → Disable workflow. Уже отправленный запрос
к модели может продолжиться у провайдера; при необходимости отзовите ключ.
GitHub App и ключ подключаются владельцем отдельно; наличие workflow само по себе
не подтверждает успешный ответ модели.

Источники: [GitHub integration](https://opencode.ai/docs/github/),
[обнаружение скиллов](https://opencode.ai/docs/skills/),
[модель OpenAI](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

### Автотриаж входящих обращений

Событие `issues: opened` запускает отдельное задание `triage` с собственным
`prompt` в [opencode.yml](.github/workflows/opencode.yml). Допускаются авторы
типа `User` с ролью `OWNER`, `MEMBER` или `COLLABORATOR`. Для остальных авторов
доверенный участник может вызвать разбор комментарием `/oc`.

Спецификации и тикеты скиллов создаются сразу с `ready-for-agent` и пропускаются.
Также пропускаются `ready-for-human` и `wontfix`. Фильтр действует перед запуском
задания и повторно по актуальному issue перед вызовом модели. Правила меток —
[triage-labels.md](docs/agents/triage-labels.md), разделение обращений и готовых
заданий — [issue-tracker.md](docs/agents/issue-tracker.md).

Автотриаж читает описание, всю переписку, инструкции, словарь, ADR и код,
проверяет существующее поведение и оставляет один предварительный разбор
с вопросами и следующим шагом. Комментарий содержит AI disclaimer и маркер
`<!-- auto-triage:v1 -->` для защиты от повторного разбора. Код не меняется.
Состояние — `needs-info`, если нужны ответы, иначе `needs-triage`.

Права автотриажа: `contents: read`, `issues: write`; `GITHUB_TOKEN` и `GH_TOKEN`
используют токен Actions (`use_github_token: true`), без OIDC и прав записи
в код или PR. API-ключ передаётся проверке наличия секрета и шагу модели.
Тайм-аут задания — 10 минут.
Группа `opencode-triage-<repository>` допускает один активный автотриаж на весь
репозиторий, `cancel-in-progress: false`. GitHub хранит один ожидающий запуск
и может заменить его новым: это ограничитель нагрузки, а не надёжная очередь.
Если обращение было вытеснено, вызовите `/oc` вручную. Ручные вызовы имеют
свою группу на номер issue/PR и могут работать одновременно с автотриажем.

Порядок работы:

1. Создайте issue словами пользователя, без технического решения.
2. Ответьте на вопросы автотриажа; для продолжения используйте
   `/oc разбери обращение по скиллу triage, предложи следующий шаг, код пока не меняй`.
3. После согласования поведения вызовите `to-spec`, затем `to-tickets` по всей
   переписке. Проверьте основной, негативный и соседний сценарии, границы тестов
   и зависимости. При изменении API сохраняется TypeSpec и генерация.
4. **Человек** пишет в исходном issue итоговый комментарий со ссылками на
   спецификацию и все тикеты. `ready-for-agent` само по себе его не заменяет.
5. Перед `implement-spec` агент читает связанные материалы и зависимости.
   PR реализации содержит ссылку на комментарий согласования. Существенные
   изменения поведения или объёма снова согласуются с человеком.

Пример текущей доработки: [обращение #3](https://github.com/AlekseiGerasimov/ai-for-developers-project-387/issues/3),
[спецификация #4](https://github.com/AlekseiGerasimov/ai-for-developers-project-387/issues/4),
[запись с темой #5](https://github.com/AlekseiGerasimov/ai-for-developers-project-387/issues/5)
→ [показ владельцу #6](https://github.com/AlekseiGerasimov/ai-for-developers-project-387/issues/6).
Итоговое подтверждение человеком ожидается в исходном обращении.

Проверка фильтров локально: `mise exec -- node --test .github/scripts/triage-policy.test.cjs`.
Проверка workflow: `mise exec -- actionlint -shellcheck= -pyflakes=`.
После попадания workflow в default branch проверьте Actions на двух новых issue:
обычное обращение доверенного автора должно получить предварительный разбор;
проверочный подготовленный тикет, созданный **сразу** с `ready-for-agent`, должен
показать `triage: skipped` без обращения к модели и без комментария автотриажа.
Сохраните ссылки на оба запуска в исходном issue. Локальная проверка фильтров
не заменяет эту проверку событий GitHub и доступности провайдера.

## Docker и публикация

Сборка из корня репозитория и запуск с автоматическим стартом приложения:

```bash
docker build -t calendar .
docker run --rm -p 8080:10000 -e PORT=10000 -v calendar-data:/app/data calendar
```

Откройте `http://localhost:8080`. Spring Boot обслуживает интерфейс и API одним
процессом, слушает `PORT` (по умолчанию 8080). Node.js и JDK нужны только для сборки;
контейнер запускается от непривилегированного пользователя.

Данные хранятся в файловой H2 `/app/data/calendar`. С volume `calendar-data` они
сохраняются после перезапуска и замены контейнера. Без volume данные переживают
остановку/старт того же контейнера, но удаляются при его удалении или замене.
На Render Free постоянного диска нет: после повторного деплоя или пересоздания
экземпляра каталог и записи сбрасываются. Приложение рассчитано на одну копию.

### Render MCP без секретов

Безопасный шаблон конфигурации Codex: `codex-render.config.toml.example`.
Скопируйте его в `.codex/config.toml` (создайте каталог `.codex`), откройте проект
как доверенный и выполните `codex mcp login render`. В Windows PowerShell при
запрете запуска скриптов используйте `codex.cmd mcp login render`.
Завершите OAuth в браузере и перезапустите сессию агента, чтобы появились инструменты
Render. Данные OAuth сохраняются в пользовательском хранилище Codex вне проекта;
не копируйте их в репозиторий. Локальные `.codex/config.toml`, `.codex/auth.json`
и `.env*` исключены из Git. Шаблон ключей не содержит.

Инструкции: [Render MCP](https://render.com/docs/mcp-server),
[Codex MCP](https://learn.chatgpt.com/docs/extend/mcp).
Альтернатива — подключить Render в списке интеграций агента через OAuth.

После входа выберите рабочее пространство Render и создайте Docker Web Service
из этого репозитория: Dockerfile `./Dockerfile`, контекст `.`, одна копия,
проверка состояния `/api/meeting-types`, `PORT=10000`; команда запуска берётся
из образа. Эти параметры также описаны в `render.yaml`. Для сохранения данных
между деплоями нужен постоянный диск, смонтированный в `/app/data`, с правом
записи для UID 10001.

Приложение опубликовано: **https://calendar-se8k.onrender.com** (Render Free,
Frankfurt, автоматический деплой из `main` исходного проекта 386).
Этот адрес относится к предыдущему проекту; для запуска текущего кода используйте Docker-команды выше.

Проверено 15 ноября 2026 года на коммите `d84aaa0`: главная, каталог,

## Пользовательский сценарий

«Запись на звонок» — упрощённый сервис по мотивам [Cal.com](https://cal.com).
Владелец календаря один и задан заранее; гость записывается без регистрации.
Ниже описан целевой сценарий приложения, которое предстоит реализовать.

1. **Создание типа встречи.** Владелец открывает список типов встреч и создаёт
   «Знакомство»: описание «Обсудим задачу и дальнейшие шаги», длительность 30 минут.
   Сохранённый тип появляется в публичном каталоге встреч.
2. **Выбор встречи.** Гость открывает каталог, выбирает «Знакомство» и видит
   описание, длительность и календарь записи на ближайшие 14 календарных дней.
3. **Выбор времени.** Гость выбирает доступный день, затем свободный слот.
   Например, встреча с началом в 10:00 длится до 10:30. На странице указан
   часовой пояс, чтобы время записи было однозначным.
4. **Подтверждение записи.** Гость вводит имя и email, проверяет тип встречи,
   дату и время и подтверждает запись. Приложение показывает подтверждение
   с деталями встречи. Имя и email — предлагаемые поля для нашего приложения;
   окончательный состав формы будет зафиксирован в спецификации.
5. **Просмотр владельцем.** Владелец открывает общий список предстоящих встреч
   всех типов и видит новую запись: тип встречи, дату, время и данные гостя.
6. **Защита занятого времени.** Интервал 10:00–10:30 больше нельзя забронировать,
   в том числе частично пересекающейся встречей другого типа. Следующая встреча
   может начинаться в 10:30. Если два гостя одновременно подтверждают
   пересекающиеся интервалы, запись получает только один; второму предлагается
   выбрать другое свободное время.

В проект не входят авторизация, личные кабинеты, внешние календари и уведомления.
Начало 14-дневного окна, рабочие часы, часовой пояс и шаг доступных стартов
будут определены в спецификации, а не на этапе изучения референса.

## Установка

Установите [mise](https://mise.jdx.dev/getting-started.html) и добавьте его в PATH.
Минимальная версия mise и версии инструментов закреплены в `mise.toml`,
Maven Wrapper и `package-lock.json`.

В `package.json` временные `overrides` закрывают уязвимости зависимостей инструментов;
при обновлении инструментов их следует пересмотреть.

На Windows mise должен быть доступен в обычном терминале и терминале IDE.
После установки добавьте каталог с `mise.exe` в PATH и перезапустите терминал.
Проверка: `mise --version`.

Git-хуки запускают проверки через `mise exec`, чтобы использовать версии
инструментов из `mise.toml`. Сам `mise` должен быть установлен в постоянный
каталог и доступен в PATH процесса Git. После изменения PATH перезапустите IDE.
Для переустановки хуков выполните `mise exec -- hk install --mise`.

```bash
git clone https://github.com/AlekseiGerasimov/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise trust
mise install
mise run setup
```

## Использование

```bash
mise run dev
```

Откройте http://localhost:5173: главная страница «Запись на звонок» объясняет
сценарий записи без регистрации. Ссылка «Выбрать встречу» ведёт на `/meetings` —
каталог типов встреч с названием, описанием и длительностью из API.
Новый каталог пуст («Пока нет типов встреч»); демонстрационные данные не создаются.
Владелец создаёт типы на `/owner/meeting-types`. Ссылка типа ведёт на
`/meetings/{id}`: описание и выбор дня и времени на ближайшие 14 календарных
дней по Europe/Moscow. Первый свободный день выбран автоматически, время
выбирает гость. Создание записи будет добавлено следующим тикетом.

Бекенд отвечает на http://localhost:8080/api/health. Vite проксирует `/api`
на бекенд. `GET /api/meeting-types` возвращает каталог из файловой H2.
`GET /api/meeting-types/{id}` возвращает тип, а
`GET /api/meeting-types/{id}/slots` — свободные интервалы и границы окна.
Flyway создаёт схему при первом запуске. По умолчанию данные сохраняются
в `./data/calendar` относительно рабочей папки сервера. Путь можно задать
переменной `CALENDAR_DATABASE_PATH` или `--spring.datasource.url=jdbc:h2:file:/path/calendar;LOCK_TIMEOUT=5000`.
На один файл БД допускается одна работающая копия приложения.

Термины проекта записаны в [GLOSSARY.md](GLOSSARY.md), принятые решения —
в [docs/adr/](docs/adr/). Правила записи определены в спецификации #10.

Серверы работают в фоне под управлением mise/pitchfork:

```bash
mise daemons status
mise daemons logs backend
mise daemons stop backend frontend
```

### Запуск собранного приложения

```bash
mise run build
java -jar backend/target/calendar.jar
```

Откройте http://localhost:8080/. Один Spring Boot сервер отдаёт главную,
каталог на `/meetings` и API на `/api/health` и `/api/meeting-types`. Прямое открытие и обновление
`/meetings` поддерживаются. Vite и Node.js для запуска готового JAR не нужны;
для команды `java` используйте Java из окружения mise (`mise exec -- java ...`),
если она не доступна напрямую в PATH.

Задачи `build`, `test` и `check` сначала собирают фронтенд. Maven включает
`frontend/dist` в JAR. `test` и `check` очищают только скопированные статические
ресурсы, исключая устаревшие JS/CSS, и работают при запущенном JAR.
`check` выполняет Maven `verify` с профилем `checks` в отдельном каталоге
`backend/target/check`, не перезаписывая запущенный `backend/target/calendar.jar`.
Для прямого запуска Maven-тестов предварительно выполните
`mise exec -- npm run build --workspace frontend`.

`build` сохраняет Maven `clean`: перед сборкой остановите запущенный JAR,
так как на Windows работающий процесс блокирует его удаление.

Команды из корня репозитория (Windows и Linux):

| Команда                       | Назначение                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------- |
| `mise run install`            | Установка npm-зависимостей из lockfile без Git-хуков (для CI)                |
| `mise run check`              | Актуальность генерации, линтеры, типы, сборка, Vitest, HTTP/JUnit и Chromium |
| `mise run lint`               | Checkstyle, ESLint, Prettier и actionlint                                    |
| `mise run lint:commit`        | Те же линтеры с Maven offline после начальной установки                      |
| `mise run audit`              | Сетевой аудит npm, ошибка при high/critical                                  |
| `mise run test`               | Vitest: состояния каталога; HTTP/JUnit: сервер, H2 и JSON                    |
| `mise run test:e2e`           | Отдельный JAR: каталог, создание типов и календарь в Chromium desktop/mobile |
| `mise run build`              | Сборка фронтенда и исполняемого JAR                                          |
| `mise run generate`           | OpenAPI, клиентский SDK и Java-интерфейсы из TypeSpec                        |
| `mise exec -- npm run format` | Форматирование исходников и конфигураций                                     |

Контракт находится в `contracts/main.tsp`, сервер — в `backend/`,
интерфейс — в `frontend/`. После изменения TypeSpec выполните генерацию
и включите обновлённые `contracts/openapi.yaml` и `frontend/src/api/` в коммит.
Java-интерфейсы генерируются в `backend/target/` и не коммитятся.

Перед первым браузерным прогоном установите Chromium:

```bash
mise exec -- npx playwright install chromium
mise run test:e2e
```

В Linux CI используется `playwright install --with-deps chromium`.
Браузерный прогон собирает собственный `backend/target/e2e/calendar.jar`,
создаёт временную файловую H2 с тестовым каталогом и запускает Java на свободном
порту (`server.port=0`). После успеха или ошибки созданный процесс останавливается,
БД удаляется. Пользовательский сервер и его JAR/БД не затрагиваются.
Только собственный браузерный сервер запускается с профилем `e2e` и
фиксированными часами (2026-11-16T06:00:00Z); обычный запуск использует
реальное серверное время. Публичного API изменения времени нет.
HTTP/JUnit также использует изолированные H2; заполнение каталога — только
тестовая подготовка. Данные проверяются через HTTP, а не чтением таблиц.

GitHub Actions запускает `mise run check` на каждый push и pull request.
`mise run setup` предварительно загружает зависимости линтера и устанавливает Git-хуки.
Pre-commit вызывает только `mise run lint:commit`, без сборки, тестов и сетевых запросов;
commit-msg проверяет Conventional Commits, например `feat: add meeting types`
или `chore: scaffold application`. Release-please собирает release-PR после мержа в main.

### Проверка перед коммитом и Maven-кэш

`mise run lint:commit` запускает Checkstyle с флагом Maven `--offline`, чтобы
проверка перед коммитом не обращалась к сети. Для этого инструменты должны быть
установлены, а зависимости Maven — уже загружены. Первоначальный `mise run setup`
выполняется с доступом к интернету: он устанавливает npm-зависимости, запускает
линтеры онлайн для заполнения Maven-кэша и затем устанавливает Git-хуки.

Если очистить `~/.m2` (на Windows — `%USERPROFILE%\.m2`), offline-проверка может
завершиться ошибкой о недоступном в кэше плагине или зависимости. Подключитесь
к интернету и выполните из корня проекта:

```bash
mise run lint
mise run lint:commit
```

Первая команда разрешает Maven скачивать недостающие зависимости; вторая
проверяет, что линтеры снова работают без сети. После успешной проверки повторите
коммит. Переустанавливать npm-зависимости и Git-хуки для восстановления Maven-кэша
не требуется. При обновлении Maven-плагинов также сначала выполните `mise run lint`.

### Регулярный аудит зависимостей

[Dependency audit](.github/workflows/security.yml) проверяет npm-зависимости
приложения `calendar-workspace`, включая devDependencies, по `package-lock.json`.
Адрес приложения и `APP_URL` не требуются: это аудит зависимостей, не Lighthouse.
Расписание `17 3 * * *` — ежедневно в 06:17 по Москве (UTC+3).
GitHub может задерживать или пропускать запуски; workflow должен находиться
в основной ветке и быть включён. В публичном репозитории расписание отключается
после 60 дней без активности. Лимит job — 20 минут, агента — 12 минут;
общая concurrency-группа сериализует ручные и плановые аудиты.

Ручная проверка: Actions → Dependency audit → Run workflow → ветка `main`.
Без `demo` собирается настоящий `npm audit --json --package-lock-only`.
С `demo=true` используется подготовленная **учебная** находка
`synthetic-training-package / training-001`, не подтверждающая дефект приложения.
Повторный запуск с `demo=true` проверяет отсутствие дубликатов.

JSON-отчёт, диагностические данные и контекст сохраняются в `$RUNNER_TEMP`,
вне рабочего дерева. На странице прогона доступны артефакты
`dependency-audit-<run_id>-<attempt>` и `dependency-audit-analysis-<run_id>-<attempt>`
(хранение 30 дней); итог агента также находится в Summary.
Содержательные выводы сохраняются надолго в журнале GitHub Issues.
По каждой новой high/critical находке агент создаёт отдельный issue с проблемой,
предлагаемым действием, advisory, SHA и ссылкой на прогон. Он ищет дубли среди
открытых и закрытых issues по маркеру и смыслу; одинаковые комментарии не добавляет.
Новые обращения получают `needs-triage`: решение о реализации принимает человек.
PR автоматически не создаётся. Ошибка сбора означает «нет данных», а не
«проблем нет» или «исправлено». Уязвимости не блокируют обычный CI приложения.

Авторизация агента: `use_github_token: true`, `contents: read`, `issues: write`;
права на запись кода, PR и OIDC ему не выдаются. Ключ провайдера находится только
в GitHub Actions Secret `OPENAI_API_KEY`, токен — в `github.token`.
Workflow передаёт их через окружение только шага агента, не печатает значения
и не сохраняет их в отчётах; публикация сессии отключена (`share: false`).
В prompt отдельно запрещено читать и выводить секреты.
Параметры авторизации сверены с [документацией OpenCode](https://opencode.ai/v1/docs/github/).

Локально проверены actionlint, форматирование, ESLint и тесты сборщика:
учебная находка явно помечена; отсутствие lockfile даёт «нет данных».
